My Workspace: Fixing a Scattered Workday with AI

My work lived in six places, and every morning went into stitching them together. I traced the real cost to the connecting, not the tasks, and designed a single workspace where AI links my projects, to-dos and messages for me.

Who it serves
  • Me first: one knowledge worker juggling many projects
  • Then colleagues, through a test-drive copy and a build-your-own guide
My role
I was the problem owner, designer and builder.
I ran the whole cycle: problem diagnosis, requirements and guardrails, prompt design, iterative prototyping with an AI partner, and enablement for colleagues.
Tools used
  • Claude (build partner + scheduled tasks)
  • Microsoft 365: Outlook, Teams, OneDrive
  • Electron (HTML/CSS/JavaScript)
?

Problem

My work was spread across six tools that didn't talk to each other:

  • Six sources. Calendar, email, Teams, a to-do list, notes and a project tracker.
  • Manual stitching. Each morning went into matching messages to the projects they affected.
  • Late surprises. A rescheduled meeting or a new request could quietly put a milestone at risk.

Result: the real work could only start after the morning went into piecing things together.

→

Solution

I designed a connected personal workspace where AI does the stitching:

  • One window. Schedule, to-dos, projects, notes and a weekly review together.
  • Automatic connections. An hourly AI task matches new emails and Teams messages to my projects.
  • Early warnings. It raises an alert on the affected project and suggests a to-do I can add or dismiss.

Result: changes surface before they become problems.

How I solved it

1

Diagnose the real problem

The easy answer would have been a better to-do app. Before building anything, I did a small needs analysis on myself: I listed where my work lived and what I did by hand each morning.

The pattern was clear. Having too many tasks wasn't the problem. The cost was in connecting information: reading a Teams message, remembering which project it touched, checking whether it moved a deadline, and then writing a to-do somewhere else. Another place to store tasks would have added a seventh tool.

The reframeNot "where do I keep my tasks?" but "how do I stop being the person who connects everything by hand?" That question shaped every decision that followed.

2

Set guardrails before features

I work at a university, so the solution had to be safe before it could be useful. I wrote down the constraints first and treated them as requirements:

  • Read-only. The AI can read my calendar, email and Teams, but it can never send, reply or change anything.
  • My data, my folder. Everything is stored as plain files in my own OneDrive. No separate server, account or sign-in.
  • No student records. Notes that look like they contain an SSN, ID number, phone number or student email are blocked from being sent to AI.
  • Humans decide. AI only suggests. Every to-do, alert and project plan waits for me to add, edit or dismiss it.
  • Built for one person. I kept it a personal tool on purpose, which kept it simple and kept other people's data out.
3

Prototype one screen, then iterate

Instead of specifying the whole system up front, I described one screen, the dashboard, to Claude in plain language and asked for a clickable preview.

Then I used rapid iteration: open the preview, note what was off or missing, share a screenshot, and change one thing at a time. Each round was a small test against how I actually work, the same loop I use when I prototype a course with learners.

I added features only when a real need came up. Quick add, for example, lets me save a thought from any program without switching windows.

4

Solve the connection problem

This was the hardest part and the core of the project. I needed Microsoft 365 data in the tool without building a sign-in or an integration I'd have to maintain.

Decision: let a scheduled AI task do the reading

Every weekday hour, a read-only Claude task reads my Outlook calendar, email and Teams and writes a small summary file into my OneDrive folder. The app just reads that file. Keeping the two parts separate meant the app never touches my accounts, and either side can change without breaking the other.

Decision: make the prompt do the connecting

I wrote the task's prompt so Claude checks every message against the projects and to-dos already in the tool. When an email or Teams message touches a project I track, it adds an alert to that project. When action is needed, it suggests a to-do. It also flags schedule conflicts and suspicious emails.

For example, if a colleague writes in Teams that a review has moved to Friday, the dashboard flags that the change squeezes an upcoming feedback milestone and offers a to-do to respond.

5

Connect the rest of the work

With the connection engine working, I made sure nothing inside the tool stood alone either:

  • Projects hold the goal, milestones, tasks, notes and documents. Tasks follow their milestone date if it moves.
  • Plan with AI drafts milestones and tasks from a description or a document, and I review them before anything is created.
  • Notes link to projects, and AI can suggest to-dos from a meeting note.
  • Weekly Review shows what got done and how each project moved, so I can reflect and adjust.
6

Turn a personal fix into something others can use

Once it worked for me, I wanted colleagues to benefit too. Since everyone works differently, I didn't want to hand out my tool as the answer. I designed the rollout as a learning experience instead:

  • A test drive. Colleagues can try a clean copy with their own data for a few weeks and notice what helps.
  • A build-your-own path. A short guided interview and ready-to-copy prompts for each feature help people build a version around their own workflow.
  • The method, not just the tool. I documented the six steps I followed: name the problem, describe it, refine the preview, connect Microsoft 365, package the app, and keep improving.

Results

  • One window instead of six. My day, projects, notes and to-dos live together.
  • Problems surface early. Schedule changes and new requests show up on the project they affect, with a suggested next step.
  • A repeatable method. Colleagues can test-drive the tool or build their own using the prompts and steps I wrote.

What this project shows

How I approach problemsI look for the root cause before the obvious fix, set guardrails before features, prototype small and iterate with real use, and then turn what I learned into something others can learn from. It's the same process I use to design learning, applied to my own workflow.
